# Compile-time constants

This example shows namespaced constants generated by `#[copper_runtime]` and constants
merged from a normal Copper RON include. Constants without `module:` are generated under
`constants`; an explicit relative module path generates a macro-owned module tree.

- `constants::MAX_DETECTIONS` is a primitive `usize` in the default module.
- `frames::camera::CAMERA_TRANSLATION` omits both `storage` and `unit`, so it is `f32`
  meters.
- `frames::camera::CAMERA_OFFSET` supplies millimeters, which are normalized to the same
  f32 meter storage.
- `control::CONTROL_PERIOD` selects `f64` while keeping the default coherent SI unit
  (seconds).
- `control::YAW_LIMIT` selects both `f64` and degrees; the generated value stores radians.

The generated modules are owned by the macro. A configured module path therefore cannot
name a module already declared by the application. Module placement only controls the Rust
namespace; it does not change mission applicability.

Constants use the same root-first include precedence as tasks and resources: when the root
file and an include declare the same `(module, id)`, the root declaration wins. The same
`id` may be used in different modules. Constants are baked into the binary. If a runtime
robot configuration changes a compiled constant, Copper emits a warning and keeps the baked
value.

`main.rs` also builds const `WorldFrame -> RobotFrame` and `RobotFrame -> CameraFrame`
`TypedTransform3D`s directly from the generated translation/rotation quantities, then composes
them into a const `WorldFrame -> CameraFrame` transform. The shared intermediate frame is a type
parameter, so trying to compose transforms whose frames do not meet is a compile-time error. Only
the timestamp is added at runtime, when the static transform is turned into a message.
